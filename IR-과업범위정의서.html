1. 과 업 개 요

1.1 과업 목적

회사 홈페이지의 내용이 코드에 고정되어 있으면 공지 한 건, 제품 소개 한 줄을 고치는 데에도 개발과 배포가 필요하다. 그 결과 사이트는 구축 시점에 멈추고, 최신 소식과 특허 · 인증이 실제보다 뒤처진 상태로 남는다. 도입을 검토하는 방문자의 문의도 전화와 이메일로만 들어와, 누가 언제 무엇을 물었고 답했는지가 남지 않는다.

본 과업은 방문자가 이용하는 회사 사이트와 그 내용을 운영자가 직접 관리하는 서비스를 한 쌍으로 구축하여, 운영 주체가 개발 의존 없이 사이트를 현행으로 유지할 수 있도록 하는 것을 목적으로 한다.

도입을 검토하는 방문자에게는 제품이 어떤 문제를 어떻게 푸는지를, 거래를 검토하는 상대에게는 회사가 무엇을 해 온 곳인지를 각각의 경로에서 답한다.

두 서비스는 동일한 데이터를 참조한다. 데이터를 이중으로 관리하면 어느 쪽이 기준인지 확인할 방법이 없어지기 때문이다. 따라서 관리자의 변경은 사이트에 그대로 반영된다.

1.3 수행 단계

본 과업은 두 단계로 나누어 수행한다. Back-End 는 제외 범위가 아니라 2단계의 수행 범위이며, 1단계에서 확정한 요구사항이 그대로 2단계의 착수 명세가 된다.

단계수행 범위완료 기준
1단계기획 · UI 디자인 · Front-End 구현 · Back-End 요구사항 정의화면 63개가 정의대로 동작하고, Back-End 요구사항이 서버 개발에 착수할 수 있는 수준으로 확정된 상태. 상세 기준은 5.2 참조.
2단계서버 애플리케이션 · 데이터베이스 · API · 인증 및 권한 · Front-End 연동정의한 규칙이 서버에서 지켜지는 상태. 상세 기준은 5.4 참조.

1.4 전제 조건

  • 1단계 시점에는 서버와 데이터베이스가 없다. 화면이 참조하는 데이터는 공통 데이터 구조로 관리하며, 관리자의 변경은 브라우저 세션 범위에서 유지된다. 2단계에서 실제 서버로 대체한다.
  • 제품 · 서비스 소개 원고와 회사 정보는 발주처가 제공한다. 본 과업은 제공된 콘텐츠를 화면에 반영하는 범위까지 수행한다.
  • 제품과 서비스는 화면 구조가 코드에 있어 문구만 관리한다. 제품을 늘리는 것은 별도 협의 대상이다.
  • 오시는 길 화면은 카카오 지도를 사용한다. 키 발급과 도메인 등록은 발주처 계정으로 수행해야 하며, 상세 준비 사항은 「요구사항 정의서」에 있다.

3. 책 임 범 위

책임 범위에서 실제로 다투는 것은 담당 여부가 아니라 어디까지 수행하면 완료인가다. 따라서 각 영역에 대해 수행 목적 · 제공 범위 · 주요 산출물 · 완료 기준 · 제외 범위를 함께 정의한다.

구분수행 목적제공 범위주요 산출물완료 기준제외 범위

  • 화면 목록 · 세부 기능 · 데이터 항목이 문서와 코드에서 일치한다.
  • Back-End 요구사항 정의가 5.3 의 완료 기준 열 가지를 충족한다.

  • 범위 밖으로 정의된 항목이 구현되지 않은 사실은 미완료가 아니라 범위 제외로 판정한다.
  • 2단계 구현 대상으로 표기된 항목은 1단계 인수 판정 대상이 아니다.

5.3 Back-End 정의 완료 기준 (1단계)

다음 조건을 모두 충족한 경우 Back-End 정의가 완료된 것으로 판단한다. 정의 내용은 「기능 명세서」에 있다.

  • 주요 관리 대상과 데이터 구조가 정의되어 있다.
  • 화면별로 필요한 데이터 항목이 정의되어 있다.
  • 데이터 간 주요 관계가 정의되어 있다.
  • 필요한 조회 · 등록 · 수정 · 삭제 연산이 식별되어 있다.
  • 주요 API 인터페이스 요구사항이 정의되어 있다.
  • 입력값 및 데이터 검증 정책이 화면 검증과 서버 검증으로 구분되어 정의되어 있다.
  • 노출 · 공개 · 처리 상태 등 상태값 정책과 전이 규칙이 정의되어 있다.
  • 관리자 기능에 필요한 권한 요구사항이 정의되어 있다. 등급 체계 자체는 발주처 확정 대상으로 표시되어 있다.
  • 주요 예외 상황과 오류 응답 요구사항이 정의되어 있다.
  • 후속 Back-End 개발자가 Front-End 화면을 다시 분석하지 않고 서버 개발에 착수할 수 있는 수준으로 문서화되어 있다.

5.4 2단계 완료 기준

1단계의 완료 기준이 「화면이 정의대로 도는가」였다면, 2단계는 「정의한 규칙이 서버에서 지켜지는가」다. 화면에서 막는 것과 서버에서 막는 것은 다른 일이므로 따로 판정한다.

  • API 요구사항에 정의된 도메인별 연산이 모두 구현되어 있으며, 화면이 공통 데이터 구조 대신 실제 API 를 호출한다.
  • 비즈니스 규칙 중 서버 검증으로 표기된 항목이 서버에서 차단된다. API 를 직접 호출해도 규칙이 적용되어야 한다.
  • 상태 전이 규칙이 구현되어 있으며, 정의되지 않은 상태값 요청은 거부된다.
  • 권한 등급이 구현되어 있고, 미인증은 401 · 등급 부족은 403 으로 구분되어 응답한다.
  • 예외 상황에 대해 정의된 상태 코드와 응답이 반환된다.
  • 문의가 실제로 저장되고, 첨부 파일이 보관되며, 대표 수신 이메일로 접수 알림이 발송된다.
  • 관리자 서비스의 등록 · 수정 · 삭제가 실제로 반영되며, 새로 고침 이후에도 유지된다.
  • 약관과 처리방침을 공개로 전환하면 사이트의 해당 화면이 준비 중 안내에서 본문으로 바뀐다.
  • 방문 통계가 실제 수집 데이터로 표시된다.
  • 데이터 보존 · 파기 기준이 배치 처리로 동작하며, 파기 기록이 남는다.
  • 기능 명세서의 화면별 검수 기준이 서버 연동 상태에서 다시 통과한다.

6. 변 경 관 리 기 준

단계기준까닭
접수변경 요청은 요구 ID 또는 기능 ID 를 지목해 제기한다.REQ-C-02 처럼 지목하면 네 문서의 같은 자리를 함께 찾을 수 있다. 화면 이름으로 지목하면 목록 · 상세 · 등록 중 어느 화면인지 특정되지 않는다.
판단요청을 범위 내와 범위 외로 나눈다.이미 정의된 기능의 표현 · 배치 · 문구 조정은 범위 내 변경이다. 화면 추가, 신규 데이터 항목 도입, 4장에서 제외 범위로 정의된 항목의 수행은 범위 외이며 별도 협의 대상이다.
반영변경은 화면 등록부와 화면 명세의 수정으로 시작한다.그 둘을 고치면 네 문서가 함께 갱신되고, 저장소의 검사 도구가 빠진 곳을 잡아낸다.
문서만 수정하거나 코드만 수정하는 변경은 허용하지 않는다.한쪽만 반영되면 다른 쪽이 낡은 상태로 남고, 그 사실은 인수 시점에 드러난다.
기록변경 이력은 저장소의 이력으로 갈음한다.별도 변경 관리 대장을 두지 않는다. 두 벌이 되면 한쪽만 기록되고, 그때부터 어느 쪽이 기준인지 확인할 수 없게 된다.
