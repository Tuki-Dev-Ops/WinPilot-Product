1. 프 로 젝 트 개 요

1.1 프로젝트 목적

브랜드 사이트의 내용이 코드에 고정되어 있으면 가격 한 줄, 공지 한 건을 변경하는 데에도 개발과 배포가 필요하다. 그 결과 사이트는 구축 시점에 멈추고, 실제 운영은 사이트 밖에서 이루어진다.

본 과업은 고객이 이용하는 서비스와 그 내용을 운영자가 직접 관리하는 서비스를 한 쌍으로 구축하여, 운영 주체가 개발 의존 없이 서비스를 현행으로 유지할 수 있도록 하는 것을 목적으로 한다.

두 서비스는 동일한 데이터를 참조한다. 데이터를 이중으로 관리하면 어느 쪽이 기준인지 확인할 방법이 없어지기 때문이다. 따라서 관리자 서비스의 변경은 고객 서비스에 그대로 반영되며, 반영 범위는 3.3 「데이터 변경 영향도」에 정의한다.

1.3 수행 단계

본 과업은 두 단계로 나누어 수행한다. Back-End 는 제외 범위가 아니라 2단계의 수행 범위이며, 1단계에서 확정한 요구사항이 그대로 2단계의 착수 명세가 된다.

단계수행 범위완료 기준
1단계기획 · UI 디자인 · Front-End 구현 · Back-End 요구사항 정의화면 47개가 정의대로 동작하고, 6장의 요구사항이 서버 개발에 착수할 수 있는 수준으로 확정된 상태. 상세 기준은 5장 참조.
2단계서버 애플리케이션 · 데이터베이스 · API · 인증 및 권한 · Front-End 연동정의한 규칙이 서버에서 지켜지는 상태. 상세 기준은 6.11 참조.

1.4 전제 조건

  • 1단계 시점에는 서버와 데이터베이스가 없다. 화면이 참조하는 데이터는 공통 데이터 구조로 관리하며, 관리자 서비스의 변경은 브라우저 세션 범위에서 유지된다. 2단계에서 실제 서버로 대체한다.
  • 메뉴 이미지 및 콘텐츠 원고는 발주처가 제공한다. 본 과업은 제공된 콘텐츠를 화면에 반영하는 범위까지 수행한다.
  • 브랜드 로고는 원본 파일을 제공받아 사용한다.

6.5 비즈니스 규칙 및 검증 정책

화면 검증과 서버 검증을 구분하여 정의한다. 화면에서 막는 것은 사용자를 돕기 위한 것이고, 서버에서 막는 것은 데이터를 지키기 위한 것이다. 화면에만 검증을 두면 API 를 직접 호출하는 요청에는 적용되지 않는다.

관리 대상규칙적용 위치

6.8 예외 및 오류 요구사항 정의

화면에서 고려해야 하는 예외 상황과 서버 응답 요구사항을 함께 정의한다.

상황발생 조건시스템 처리 · 화면 표시
존재하지 않는 데이터 조회요청한 식별자에 해당하는 데이터가 없습니다.서버는 404 로 응답한다. 화면은 목록으로 돌아가는 경로와 함께 없는 대상임을 안내한다.

6.9 Back-End 정의 완료 기준 (1단계)

다음 조건을 모두 충족한 경우 Back-End 정의가 완료된 것으로 판단한다.

  • 주요 관리 대상과 데이터 구조가 정의되어 있다.
  • 화면별로 필요한 데이터 항목이 정의되어 있다.
  • 데이터 간 주요 관계가 정의되어 있다.
  • 필요한 조회 · 등록 · 수정 · 삭제 연산이 식별되어 있다.
  • 주요 API 인터페이스 요구사항이 정의되어 있다.
  • 입력값 및 데이터 검증 정책이 화면 검증과 서버 검증으로 구분되어 정의되어 있다.
  • 공개 · 노출 · 운영 상태 등 상태값 정책과 전이 규칙이 정의되어 있다.
  • 관리자 기능에 필요한 권한 요구사항이 정의되어 있다.
  • 주요 예외 상황과 오류 응답 요구사항이 정의되어 있다.
  • 후속 Back-End 개발자가 Front-End 화면을 다시 분석하지 않고 서버 개발에 착수할 수 있는 수준으로 문서화되어 있다.

6.11 2단계 완료 기준

1단계의 완료 기준이 「화면이 정의대로 도는가」였다면, 2단계는 「정의한 규칙이 서버에서 지켜지는가」이다. 화면에서 막는 것과 서버에서 막는 것은 다른 일이므로 따로 판정한다.

  • 6.4 에 정의된 도메인별 연산이 모두 구현되어 있으며, 화면이 공통 데이터 구조 대신 실제 API 를 호출한다.
  • 6.5 의 비즈니스 규칙 중 서버 검증으로 표기된 항목이 서버에서 차단된다. API 를 직접 호출해도 규칙이 적용되어야 한다.
  • 6.6 의 상태 전이 규칙이 구현되어 있으며, 정의되지 않은 상태값 요청은 거부된다.
  • 6.7 의 권한 등급이 구현되어 있고, 미인증은 401 · 등급 부족은 403 으로 구분되어 응답한다.
  • 6.8 의 예외 상황에 대해 정의된 상태 코드와 응답이 반환된다.
  • 4.6 의 보존 · 파기 기준이 배치 처리로 동작하며, 파기 기록이 남는다.
  • 창업 상담 신청이 실제로 저장되고, 관리자 서비스에서 상담 상태를 변경할 수 있다.
  • 관리자 서비스의 등록 · 수정 · 삭제가 실제로 반영되며, 새로 고침 이후에도 유지된다.
  • 기능 명세서의 화면별 검수 기준이 서버 연동 상태에서 다시 통과한다.

  • 변경 요청은 기능 ID 를 지목하여 제기한다. 화면 이름으로 지목하면 목록 · 상세 · 등록 중 어느 화면인지 특정되지 않는다.
  • 이미 정의된 기능의 표현 · 배치 · 문구 조정은 범위 내 변경으로 처리한다.
  • 화면 추가, 신규 데이터 항목 도입, 5장에서 제외 범위로 정의된 항목의 수행은 범위 외 변경이며 별도 협의 대상이다.
  • 변경은 화면 등록부와 화면 명세의 수정으로 시작하며, 본 문서와 기능 명세서가 함께 갱신된다.
  • 문서만 수정하거나 코드만 수정하는 변경은 허용하지 않는다. 한쪽만 반영되면 다른 쪽이 낡은 상태로 남고, 그 사실은 인수 시점에 드러난다.
